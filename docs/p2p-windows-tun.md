# Windows Fake-IP TUN 下的原生 P2P

Windows 开启 Clash/Mihomo TUN 时，协调节点、STUN 和对端可能走不同出口。
STUN 域名也可能解析到 `198.18.0.0/15`，导致 NAT 探测缺少有效服务器，无法选择合适的打洞策略。
仅为当前公网 IP 添加绕过规则，在公网 IP 变化后会再次失效。

## 代码处理

- 检测正在使用 Fake-IP 地址的网卡，按路由度量值与接口度量值之和选择实际 IPv4 默认出口。
  检测使用完整的 Windows 地址枚举；`netdev` 会过滤 Wintun 使用的接口类型 53，不能单独用于这一步。
  Hyper-V 的联网 `vEthernet` 仍可作为出口，不能按“虚拟网卡”名称一概排除。
- 每个原生会话独立设置出站接口，让协调连接、STUN、UDP 监听与打洞套接字使用同一出口。
  使用 Windows `IP_UNICAST_IF`，不修改系统路由、Clash 规则或其他进程的套接字。
- UDP 监听仍绑定通配地址，以接收本机的打洞控制包；回环控制套接字、显式绑定和 IPv6 保留原有行为。
- 仅为已授权配置中的 STUN/协调域名，使用所选网卡的 DNS 服务器查询真实地址。
  校验事务、问题、CNAME 链和响应地址；域名统一为绝对名称后再比较实际 DNS 报文。
  单个补充 STUN 域名失败时保留其他可用端点，并优先为每台服务器保留一个地址。
- 每 10 秒检查选定接口及 DNS 是否变化；变化时关闭旧原生引擎。
  共享连接层在信令在线、授权有效时限频重建已关闭的原生通道，最短重试间隔为 5 秒。
  正在连接或正常工作的引擎不重复创建，关闭聊天后停止重建。
- 链路详情只为通配 IPv4 UDP 绑定补充所选接口地址，不覆盖已明确的源地址。

接口选择限于 Windows Fake-IP TUN 环境。其他原生平台共用通道恢复逻辑；普通 Web 没有原生套接字，
继续使用浏览器 WebRTC 与现有中继路径。这项改动不保证所有 VPN、NAT 或防火墙组合都能直连。
安装中的旧客户端不会因代码提交自动更新，需要重新构建并更新原生客户端。

参考：[Windows IP_UNICAST_IF](https://learn.microsoft.com/en-us/windows/win32/winsock/ipproto-ip-socket-options)、
[Mihomo TUN 配置](https://wiki.metacubex.one/config/inbound/tun/)。

## 两台 Windows 电脑的回归验证

2026-10-09，在此前失败的同一对电脑上运行修复后的连接模块，发起端临时使用原始代理配置：
TUN 保持开启，旧公网 IP 绕过规则保持原样，没有加入当前对端或 STUN 的新绕过规则。

- 发起端成功识别对称 NAT，并选用 `sym-to-cone`；第 4 次尝试完成，约一分钟建立直连。
- 两端均报告一跳 IPv4 UDP 链路；后续记录的 RTT 为 8–18 ms。
- 10 次、每次 32,768 字节的请求及回显均逐字节校验成功，共验证 327,680 字节回显。
- 测试完成后恢复先前可用的代理配置，并核对恢复结果。

这是连接模块的真实双机验证，不是已安装 GUI 版本的升级验证，也不是产品总体打洞成功率对照。
原生通道退出后的自动重建、重试间隔、续期及保留现有 RTC 通道通过共享层回归测试验证。

可使用 `crates/chat-connectivity/examples/peer_probe.rs` 重复验证。两端使用相同的临时会话名、
由 64 个十六进制字符组成的随机密钥和有效期，分别设置 `desktop: true` 与 `desktop: false`；禁止使用生产聊天授权。
将配置文件路径作为程序参数。程序最多运行 120 秒，客户端仅在直连状态下完成全部回显后输出 `PASS`。
Windows 的 `network_probe.rs` 可检查接口选择及真实 STUN 解析，输出本机网络地址但不输出密钥。

自动化测试还覆盖真实 Windows 套接字的接口绑定与回环接收、接口优先级、DNS 报文校验、
端点去重与数量上限、DNS 部分失败、显式源地址及 IPv6 的保留行为。
